# 일간보고 작성

## 작업 순서

1. 이 스킬의 `references/research.md`를 읽고 배경과 작성 기준을 확인한다. 프로젝트의 `README.md`가 있으면 함께 읽고 현재 지침을 확인한다.
2. 사용자가 제공한 원문과 대화 중 수정 요청에서 실제 활동, 배운 내용, 어려움, 느낀 점, 향후 계획을 파악한다. 원문에 있는 내용만 사용한다.
3. 보고서 작성에 꼭 필요한 정보가 부족하거나 뜻이 모호하면 해당 내용을 구체적으로 질문한다. 답변 전에는 관련 사실을 추정해 확정하지 않는다. 날짜·이름처럼 본문 작성에 필요하지 않은 정보는 질문하거나 만들어 넣지 않고 생략한다.
4. 같은 활동에 관한 내용은 한 번호 아래 묶되, 같은 실험과 관련되어 있어도 수행 목적이나 작업 내용이 다른 활동은 별도의 번호로 구분한다. 예를 들어 RO 실험 장치 복습과 Lab-scale 데이터 정리는 각각 별도의 번호로 작성한다.
5. 제목은 활동을 식별할 수 있는 짧은 이름으로 작성한다. 사용자가 지정한 명칭을 우선하며, 예시는 `1. LAP-SCALE`, `2. 토목기사 실기 공부`이다. 제목에 세부 활동을 길게 나열하지 않는다.
6. 맞춤법과 띄어쓰기를 수정하고, 의미를 유지하면서 문장을 자연스럽게 연결한다. 정중하고 간결한 `~했습니다`, `~느꼈습니다`, `~하고자 합니다` 문체를 사용한다. 원문보다 과도하게 격식을 높이지 않는다.
7. 원문과 대조하여 활동·수치·결과·단위·계획·개인정보를 임의로 추가하거나 변경하지 않았는지 확인한다. 최신 수정 요청을 전체 보고서에 반영한다.
8. 완성된 보고서를 바로 출력한다. 사용자가 요청하지 않은 작성 과정 설명이나 평가를 덧붙이지 않는다.

## 출력 형식

각 활동은 다음과 같이 번호와 간결한 제목, 본문으로 구성한다. 같은 활동 안에서 주제가 바뀌면 문단을 나눌 수 있다. 아래 대괄호는 형식 안내이며 실제 출력에는 포함하지 않는다.

```text
1. [간결한 활동명]

[실제로 수행한 활동과 배운 내용을 자연스럽게 정리한 문단]

[원문에 있는 경우에만 어려움, 느낀 점, 향후 계획을 정리한 문단]

2. [간결한 활동명]

[해당 활동의 내용]
```

활동 수만큼 번호를 붙인다. 날짜, 학교명, 작성자명, 별도 소제목은 사용자가 제공하고 포함을 요청한 경우에만 넣는다.

## 워크플로 — Workflow

단계는 아래 순서로 진행한다. 앞 단계 결과를 다음 단계의 입력으로 사용하고, 관문을 통과하지 못하면 다음 단계로 넘어가지 않는다.

1. 원문·기준 확인: research.md와 README.md를 확인하고, 원문에서 활동·수치·전문용어·요청 형식을 추린다. 중간 결과는 사실 목록이다.
   관문: 사실 목록의 각 항목을 원문 문장으로 추적할 수 있는가? 추적할 수 없으면 삭제하거나 질문한다.
2. 활동 분류와 계획: 목적과 수행 작업이 다른 활동을 나누고, 묶을 항목을 정리한다. 중간 결과는 활동별 제목·포함할 근거·불확실한 점의 개요다.
   관문: 서로 다른 작업이 단지 같은 연구 분야라는 이유로 합쳐지지 않았는가?
3. 사용자 승인: 계획과 누락 정보를 짧게 보여 주고 진행 승인을 기다린다. 승인이 오기 전에는 최종 보고서를 작성하지 않는다.
   관문: 사용자가 활동 구분과 계획을 승인했는가? 수정 요청이 있으면 계획을 고쳐 다시 확인한다.
4. 초안 작성: 승인된 활동 구분과 원문 근거만 사용해 번호별 보고서를 쓴다. 중간 결과는 초안이다.
   관문: 원문에 없는 결과·원인·일정·수치가 추가되지 않았는가? 아니면 검증 단계로 가지 않는다.
5. 자동 검증: 임시 JSON에 source_text, draft_text, missing_facts를 넣고 scripts/check_result.py를 실행한다.
   관문: PASS여야 완료할 수 있다. HOLD 또는 FAIL이면 아래 검증 규칙을 따른다.
6. 최종 출력: PASS가 확인된 보고서만 출력한다. 질문이 필요한 경우에는 보고서를 완료한 것처럼 출력하지 않는다.

## 계획 — Plan

실행 전에 사용자가 검토할 수 있도록 다음 형식으로 계획만 먼저 제시한다.

- 활동 구분: 어떤 내용을 한 번호로 묶고 나눌지
- 근거와 보존할 표현: 수치, 장비명, 용어, 어려움 등 원문에서 유지할 항목
- 확인이 필요한 정보: 보고서 사실을 확정하는 데 필요한 누락 정보

사용자가 승인하거나 수정하기 전에는 최종 문안을 작성하지 않는다. 내용이 단순해도 한 줄 계획은 보여 준다. 날짜·이름처럼 보고서 작성에 필요하지 않은 정보는 확인 질문으로 만들지 않는다.

## 검증 — Verifier

최종 출력 전에 반드시 scripts/check_result.py로 초안을 검사한다. JSON 입력은 source_text(사용자 원문), draft_text(초안), missing_facts(필수이나 원문에 없는 사실의 목록)로 구성한다.

- PASS: 번호와 제목·본문 형식, 번호 연속성, 자리표시자 부재, 원문에 없는 숫자 추가 여부가 통과된 경우에만 완료한다.
- HOLD: missing_facts가 하나라도 있으면 최종 보고서를 차단한다. 빠진 사실을 짧고 구체적으로 질문하고 답을 기다린다.
- FAIL: 형식·번호·근거 검사가 실패하면 초안을 고치고 다시 검사한다. 수정은 최대 2회다. 두 번 고친 뒤에도 실패하면 멈추고 실패 이유를 사용자에게 알린다.

검사기는 구조와 숫자 추가를 확인한다. 문맥상 활동 분류와 사실 보존의 최종 판단은 원문을 읽은 에이전트가 수행하고, 중요한 결과는 사람이 확인한다. 검사 통과를 의미적 완전성의 증명으로 과장하지 않는다.

실행 예:

~~~sh
python .agents/skills/daily-report/scripts/check_result.py review.json
~~~

## 훅·권한 — Hooks & Permissions

지침에 부탁하는 것만으로 중요한 보호를 대신하지 않는다. 훅을 지원하는 실행 환경에서는 PreToolUse 훅으로 원자료 쓰기·삭제와 허가 없는 외부 반출·파괴적 명령을 차단한다. 원자료는 읽기 전용 복사본으로 다루고, Git push·업로드·메일 발송·삭제처럼 되돌리기 어려운 행동은 준비까지만 한다. 실제 실행은 사용자가 승인한 뒤 수행한다.

아래는 Claude Code용 선택적 설정 예시다. 저장소에 자동 적용되는 설정은 아니며, 적용 전에 실행 환경과 보호 경로를 검토한다.

~~~json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "python3 .agents/skills/daily-report/scripts/check_result.py --pre-tool-use"
          }
        ]
      }
    ]
  }
}
~~~

이 예시 훅은 도구 인자를 검사해 원자료 폴더 변경과 git push, 강제 삭제 같은 명령을 거부한다. 훅을 쓸 수 없으면 같은 금지 규칙을 따르되, 검사 스크립트가 훅을 대신 실행했다고 주장하지 않는다.

## 서브에이전트 — Subagents

일간보고 한 건은 보통 한 에이전트가 처리한다. 순서가 정해져 있고 서로 의존하는 단계가 많아 기본적으로 분할하지 않는다. 여러 원문이나 긴 자료가 함께 주어진 경우에만 독립 검토를 병렬로 맡길 수 있다.

- 작업 A 목표: 원문과 초안의 수치·장비명·전문용어 대조. 결과 모양: 발견 항목, 원문 근거, 초안 위치. 도구·자료: 제공된 원문과 초안만. 경계: 문장을 직접 고치거나 사실을 추정하지 않는다.
- 작업 B 목표: 활동을 목적별로 나눈 구성이 적절한지 검토. 결과 모양: 활동별 병합/분리 의견과 근거. 도구·자료: 제공된 원문, research.md. 경계: 원문에 없는 활동을 만들지 않는다.

주 에이전트가 독립 검토 결과를 합치고, 겹치거나 충돌하는 지적은 원문으로 확인한다. 일꾼 수는 필요한 독립 검토 수만큼만 사용하며, 한 활동의 문장 작성·수정처럼 순차적인 일은 나누지 않는다.
